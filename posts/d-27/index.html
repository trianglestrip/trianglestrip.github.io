这篇日志整理 meshToBrowser 项目当前的架构、实现流程与各阶段 before/after 对比数据，并记录最近一轮"服务端可见集预测通道"从 precision 0.596 到 1.000 的完整闭环过程。所有数据都来自仓库内可复现的验证脚本与保留的 benchmark 产物，不做无 baseline 的性能宣称。

一、项目概览

仓库是一个 Nanite 风格的浏览器 WebGPU 网格查看器加离线预处理流水线：

  • viewer/：Vite + TypeScript WebGPU viewer（viewer/src/core/ 运行时渲染、流式、剔除、材质与 GPU 资源系统；viewer/src/shaders/ 为 WGSL）。
  • offline_preprocessing/：C++ 离线管线，负责 cluster 化、LOD、page/scene 资产生成。
  • scripts/：Playwright 验证、性能回归与工具脚本；基准与对比报告保留在 artifacts/。
  • docs/：架构、优化笔记与验证日志（stage-comparison.md、optimization-closure.md、visibility-prediction.md、perf-validation-log.md）。

二、实现流程

离线阶段

  1. 源 glTF 输入离线重建：cluster 化（DAG 层级）+ LOD 简化，按 per-model profile（simplify_ratio/target_error）逐文件导出 .bin 与 scene.json。
  2. build-scene-partition 读取 mesh 二进制 page table，生成 cell 化的 scene.partition.json：页面元数据含 byte range、AABB、cluster range、maxGeometricError 与稳定 priority；page AABB 按实例 transform 变换到世界坐标并在多实例间合并。
  3. 逐 bin 表面 QA 与 release gate：551 mesh stats/visual、profile calibration，全部 fail-closed。

运行时阶段

  1. 启动走 partition bootstrap：Root 页小波次优先，与 Detail 页共享 in-flight credit（峰值 16），Root 只绕过 byte/rate 预算但不饿死 Detail（压力样本 detailRequests=240、无 stale/error）。
  2. 五维统一预算（network/GPU/upload/triangle/in-flight）原子 reservation；500k triangles/frame cap 实测不超限。
  3. GPU-driven 渲染：cluster 层级遍历、frustum/screen-error/backface/Hi-Z 遮挡剔除、GPU sort/compact、indirect draw、压缩顶点 vertex pulling、progressive streaming（bounded Worker 解码 + page batch + staging ring 可选路径）。
  4. 可选 advisory 预测服务：本地 HTTP /predict 端点只改变请求顺序，页面成员、Root 回退与预算始终由本地 ScenePartitionIndex 权威决定；timeout/stale/malformed 全部自动回退本地。

六、预测通道闭环：0.596 → 1.000

这是最近一轮最有代表性的工作，过程本身值得记录：

起点：协议/降级已闭合（85/85 请求成功），但 precision 0.596、recall 1.000、waste 0.416，远低于 0.85 的建议门禁，只能 advisory。

问题一：速度单位错误。 客户端把"每次更新的位置差"直接当 camera.velocity 发给服务端，而服务端按 lookaheadSeconds 秒数外推——单位实际差约 15 倍。修复为按真实采样时间换算 world-units/second，带首样本零速、异常间隔拒绝与限幅（新增可测试纯函数 PredictionMotion.ts）。

问题二：坐标空间 bug（最有价值的发现）。 首次复测 precision 反而跌到 0.26。排查发现 scene.partition.json 里的 page.aabb 来自 bin 文件的 mesh-local 坐标，而 manifest 的 cell/mesh bounds 是世界坐标——两者根本不在一个空间。修复落在离线生成器：page AABB 按实例 transform 变换到世界坐标并在多实例间合并，重建后 2107/2107 页全部通过 mesh bounds 包含校验；服务端再加坐标兼容保护作为 fail-safe。

问题三：生命周期竞态。 模型切换时旧预测响应可能串入新模型（serial 会重置回 0）。引入 prediction epoch，异步回调需 epoch+serial 双重匹配才可写入。

问题四：真正的缺口是成员选择，不是排序。 归因分析显示服务端每次返回的选择集与基线逐字节一致（pagesReturned 395、bytesReturned 48593739 完全相同），precision 波动来自慢机采样稀释。真正差距：server 考虑全部 cell 的全部页面，本地 planner 受 maxActiveCells/maxActiveMeshes/minPagePriority 预算裁剪，每次多返回约一倍的 target 外 hints。修复为服务端完全复刻 ScenePartitionIndex.update() 的选择链，其中最隐蔽的一处语义偏差：planner 对 detail 是先按优先级截断到 maxPages−roots、再过滤 resident（不回填），而服务端此前"先过滤后截断"，导致驻留增长时 hints 持续超出 targets（precision 从 1.0 随驻留衰减到 0.49 的根因）。velocity/lookahead 降级为纯排序信号——客户端本来只用 hints 排序请求，成员 precision 不受影响。

诚实边界：precision 1.000 验证的是"服务端能精确复现本地规划"（协议与实现一致性），不是独立预测能力；预测默认仍为 advisory opt-in，网络节省声明不因此成立。

七、验证门禁

  • 全量单测：189/189 PASS（含速度单位/限幅、page AABB 世界坐标变换、server-planner 成员镜像等新增测试）。
  • Viewer 构建：54 modules PASS。
  • Frozen runtime silhouette（bistro 六视角）：6/6 PASS，2px error 0.000156。
  • 严格收敛、10×/100× shared、2×/4× expanded benchmark：全部 PASS。

八、仍保留的发布条件

  • two-phase HZB、PersistentCull、GPU 解压、timestamp-query 需跨 adapter 长样本。
  • bistro_adaptive 缺源 glTF，surface/profile gate 仍被阻断。
  • 材质、贴图、DDS、复杂二进制格式与 CRS/实例语义保持 fail-closed。
  • Root 绕过 byte/rate 预算是策略取舍；严格全局 byte cap 需要额外的 root 预置/保底策略。
  • 启动最大长帧与真实 CDN 限速策略仍需继续优化。

完整文档、可复现命令与原始 benchmark 产物见仓库 docs/ 与 artifacts/。
